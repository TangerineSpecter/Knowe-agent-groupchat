# 单用户网页版部署

网页版与桌面端共用聊天、审批和 Agent 引擎。桌面端入口仍为 Electron；网页版入口为 `python -m backend.web`。网页与桌面默认运行独立实例，数据不自动同步。不要启动两个进程直接共享同一数据目录。

## Docker Compose

在项目根目录执行 `./deploy/install.sh`。需要 Docker Engine / Docker Desktop 和 Compose v2。脚本保留已有密码、数据和自定义配置，并将实际选用的端口、基础镜像及各类下载源保存到 `.env`。

宿主机默认端口为 **18090**，被占用时向后查找空闲端口，最多检查 100 个。脚本同时检查宿主机 TCP 监听和 Docker 已发布端口，并在镜像构建结束后再次检查。以脚本最终打印的地址为准；实际端口可用 `grep '^KNOWE_PORT=' .env` 查看。访问密码见 `deploy/web-password`，登录后在设置中配置模型。镜像默认使用真实 Agent，未配置模型前必须完成首次引导。

旧脚本生成的 8090 配置，如果还没有 Knowe 容器、也没有启动过 Web 实例，会自动迁移到 18090。已经运行的 Knowe 使用的端口会保留，不会被误判为其他服务占用。可以用 `KNOWE_PORT=28090 ./deploy/install.sh` 设置起始端口；冲突时仍会自动避让并保存结果。

**新部署默认监听 `0.0.0.0`，允许内网其他电脑通过服务器 IP 和端口访问。**安装结束会检测服务器地址并打印完整链接，例如 `http://192.168.5.113:18090`。仓库不固定某一台机器的 IP，迁移到其他服务器也使用同样的默认行为。访问地址需要包含实际端口，裸 IP 默认访问 80 端口。

旧版本 `.env` 中已经保存的绑定地址会保留。已构建完成的旧部署可以执行以下命令，切换成内网访问并复用当前镜像：

```sh
git pull --ff-only
./deploy/install.sh --lan --no-build
```

`--no-build` 跳过基础镜像拉取、依赖下载和应用构建，只更新运行配置；镜像不存在时会停止并提示，不会先停止已有服务。监听地址变化时只重建 Knowe 服务，释放它原来的监听后重新检查端口占用，优先保留原端口。密码和持久数据保留。

需要仅限本机访问时，使用 `./deploy/install.sh --local`；已有镜像加上 `--no-build` 即可。也可显式配置 `KNOWE_BIND_HOST=127.0.0.1`，或者某个指定接口 IP。远程使用本机模式可通过 SSH 转发 `ssh -L 18090:127.0.0.1:18090 user@server`。HTTP 会明文传输密码，公共网络请使用 HTTPS 反向代理；服务器防火墙应允许需要访问的实际端口。

HTTPS 反向代理需要转发普通 HTTP 和 `/api/runtime/ws` WebSocket（包括 Upgrade/Connection），允许至少 65 MB 请求体，并延长 WebSocket 空闲超时。设置：

```dotenv
KNOWE_WEB_ORIGIN=https://knowe.example.com
KNOWE_WEB_SECURE_COOKIE=1
```

`KNOWE_WEB_ORIGIN` 必须精确匹配浏览器访问的来源（协议、域名、端口，不带路径）。网关不信任任意客户端提供的转发头。建议专用域名部署在 `/`，目前不支持子路径部署。

修改环境变量后运行 `docker compose up -d`。Compose 将实际宿主机端口映射到容器网关的 8090；运行时 HTTP、WebSocket 仅监听容器回环地址，内部令牌不返回浏览器。HTTPS 反向代理也应连接实际选用的宿主机端口。

## 目录与权限

| 宿主机默认目录 | 容器路径 | 用途 |
| --- | --- | --- |
| `deploy/data` | `/data` | 聊天、设置、Agent 内部状态、通知、持久签名密钥 |
| `deploy/workspaces` | `/workspace` | 项目文件、上传附件、用户缓存 |
| `deploy/web-password` | `/run/secrets/web_password` | 只读访问密码 |

新建项目默认创建 `/workspace/projects/<项目ID>`，也可选择工作根目录内已有文件夹。上传附件存放于 `/workspace/uploads`。路径持久化采用容器路径，迁移服务器时保留相同的容器挂载点。

`.env` 可设置 `KNOWE_DATA_PATH`、`KNOWE_WORKSPACE_PATH`、`KNOWE_PASSWORD_PATH`。宿主机目录须允许 `KNOWE_UID:KNOWE_GID` 读写；安装脚本默认使用执行者 UID/GID，root 首次安装和手动部署默认 1000:1000。root 安装只调整本次新建默认目录和密码文件的所有者；已有目录、自定义挂载及已有密码需要自行确认权限。镜像以普通用户运行，临时安装系统软件请修改镜像，不要在运行容器中用 root 临时修补。

基础镜像包含 Python、Node/npm、Git、Chromium、中文字体和附件文本提取依赖。项目依赖在容器中安装，避免直接复用宿主机虚拟环境或 node_modules。Agent 与服务处在同一容器、同一用户权限下；这是个人可信执行环境，不是恶意代码沙箱。不要挂载 Docker socket 或整个宿主机文件系统。

## 任务、通知与恢复

浏览器刷新、关闭、客户端休眠不会主动停止服务器已接收的任务。重连后通过现有消息回放和状态快照恢复；待审批任务按服务端配置等待或超时。发送但没有服务端确认的消息不能视作已接收。

通知中心记录审批、终态任务和异常，读状态存服务端。页面打开/恢复时汇总未读数量，不提供操作系统通知或关闭网页后的 Web Push。

容器重启属于执行进程重启，不能承诺每个外部命令无缝续跑。部署更新前先查看活动任务，等待结束或明确停止。重新打开后核对任务状态，不要盲目重发有副作用的操作。

## 更新、备份与排障

在服务器项目根目录执行一条命令即可更新：

```sh
./update.sh
```

脚本拉取当前分支所跟踪远端的更新（`git pull --ff-only`），然后执行安装脚本，复用基础镜像和构建缓存，重建服务并等待健康检查。已有配置、已选源、端口、密码和持久数据保留。更新会重启容器，请先等活动任务结束。

左侧导航底部常驻显示产品版本和构建提交短号；设置 → 关于中可查看完整提交号。版本读取自 `package.json`，安装/更新脚本自动把实际源码提交写入前端构建；本地有未提交的源码修改时，短号末尾显示 `*`，完整号带 `-dirty`。这些值属于当前页面加载的构建，更新后刷新页面即可核对。仅用 `--no-build` 调整配置会保留原镜像的版本信息。

本地 `npm run web:dev` / `npm run web:build` 会自动读取 Git 提交。直接构建 Docker 镜像而未经过安装脚本时，可通过 `KNOWE_BUILD_COMMIT` 构建参数传入提交号；未记录提交的源码包仍显示产品版本，在“关于”中注明提交未记录。

旧部署第一次需要先执行 `git pull --ff-only` 获取 `update.sh`，之后直接运行 `./update.sh`。也可以通过脚本绝对路径从其他目录运行。

源码有未提交修改、没有跟踪分支、处于 detached HEAD 或拉取失败时会停止，保留已有改动并给出错误。没有新提交时仍会执行构建和启动检查，适合重试此前未完成的部署。可用 `./update.sh --lan` 或 `./update.sh --local` 同时调整监听方式；仅更新运行配置继续使用 `./deploy/install.sh --no-build`。

- 查看日志：`docker compose logs --tail=100 -f knowe`。
- 查看健康：`docker compose ps`；HTTP 探针为 `/healthz`，不含用户数据。
- 停止：`docker compose down`（不会删除宿主机挂载目录）。
- 一致性备份：先停止容器，再备份数据目录、工作目录及密码文件。仅备份聊天数据无法恢复项目文件，丢失附件签名密钥会影响历史附件验证。
- 回退：保留上一版镜像和升级前的数据备份；数据迁移后不要直接让旧版程序读取新格式。
- 密码重置：修改密码文件，重建容器；旧登录会话失效。
- 网关无法启动：检查密码至少 12 字符、目录权限及容器日志。

## 本地开发

```sh
uv pip install --python .venv/bin/python -r backend/requirements-web.txt -r backend/requirements-dev.txt
npm ci
npm run web:build
# 另建仅本机可读的密码文件，再设置 KNOWE_WEB_PASSWORD_FILE；不要将密码写入命令历史。
PYTHONPATH=backend KNOWE_WEB_PASSWORD_FILE=/path/to/password .venv/bin/python -m backend.web
```

热更新前端使用 `npm run web:dev`，后端仍运行在 8090。Vite 代理 `/api` 到网关，浏览器访问 Vite 地址。生产使用构建后的静态文件，不运行 Vite 开发服务器。

## 隔离验收

在项目根目录、已安装上述 Python 开发依赖的环境执行：

```sh
docker build -f Dockerfile.web -t knowe-web:validation .
.venv/bin/python scripts/verify-compose-web.py
```

脚本创建独立 Compose 项目、随机密码、临时数据和模拟模型服务；实测离线执行、回放、非 root 工具运行和容器重建后的数据保留。结束后清理自己的测试容器，不读取正式实例数据或模型凭据，也不调用付费模型。日志默认保存到 `/tmp/knowe-compose-browser`（其他系统使用系统临时目录）。

增加真实浏览器 UI 验证：先执行 `.venv/bin/python -m playwright install chromium`，再给验收命令加 `--browser`。也可使用已有 Chrome，例如 macOS：

```sh
.venv/bin/python scripts/verify-compose-web.py \
  --browser-path '/Applications/Google Chrome.app/Contents/MacOS/Google Chrome'
```

UI 验证包括登录、目录选择、上传、预览下载、通知、中英文和跨标签页退出；截图输出到同一临时目录。`--image` 可指定其他已构建镜像，`--artifacts-dir` 可指定日志和截图目录。

## 构建资源与镜像源

镜像包含 Chromium 与项目执行环境，建议至少预留 4 GB 内存及 10 GB 可用 Docker 磁盘空间；构建缓存会额外占用空间。Python 部署依赖由 `backend/requirements-web.lock` 固定版本和哈希，修改 `requirements-web.txt` 后需重新生成锁文件并验证。

安装脚本实际拉取 Node、Python 基础镜像，而不是只探测仓库首页。默认优先使用 [DaoCloud 镜像服务](https://github.com/DaoCloud/public-image-mirror)，拉取报错或连续 **60 秒没有新进度输出**后回退 Docker Hub。下载和解压进度持续更新时不限制总时长，慢速下载也会继续。已配置的自定义镜像会保留；选用镜像已存在于本地时直接复用。默认优先级也适用于旧脚本保存的官方 Node、Python 镜像地址。采用 DaoCloud 且尚未配置 npm 源时，npm 源同步设为 `https://registry.npmmirror.com`。

可在 `.env` 中调整：

```dotenv
# mirror（默认）：镜像源优先；auto：官方优先，失败切换；official：只用官方基础镜像
KNOWE_DOWNLOAD_SOURCE=mirror
# 基础镜像拉取连续没有进度输出的等待秒数，不是总时限，范围 1–3600
KNOWE_PULL_TIMEOUT=60
```

直接执行 `./deploy/install.sh` 即采用镜像源优先策略，无须额外配置。需要官方源优先时，可执行 `KNOWE_DOWNLOAD_SOURCE=auto ./deploy/install.sh`，或在 `.env` 中设置该值。自定义 `KNOWE_NODE_IMAGE`、`KNOWE_PYTHON_IMAGE`、`KNOWE_NPM_REGISTRY` 会保留，私有仓库不会被替换成其他仓库。官方和镜像服务都失败时，脚本停止并提示，不会继续启动服务。

基础镜像仓库、npm、PyPI、Debian 软件包和浏览器二进制是独立的下载渠道，Docker 镜像加速不会自动加速其余渠道。安装脚本默认同时配置：

| 配置项 | 默认来源 | 用途 |
| --- | --- | --- |
| `KNOWE_NPM_REGISTRY` | `https://registry.npmmirror.com`（采用镜像基础镜像时） | 前端依赖 |
| `KNOWE_PIP_INDEX_URL` | `https://mirrors.tuna.tsinghua.edu.cn/pypi/web/simple` | Python 锁定依赖 |
| `KNOWE_APT_MIRROR` | `https://mirrors.tuna.tsinghua.edu.cn` | Debian 软件包和浏览器系统库 |
| `KNOWE_PLAYWRIGHT_DOWNLOAD_HOST` | `https://cdn.npmmirror.com/binaries/playwright` | 当前 Playwright 对应的 Chromium 和 FFmpeg |

已有自定义配置会保留；浏览器下载源显式设为空值时使用官方 CDN。`KNOWE_DOWNLOAD_SOURCE=official` 会对尚未配置的包源使用官方来源。`auto` 主要控制基础镜像的尝试顺序，包源仍按上表默认设置。

APT 软件包、pip 下载和浏览器安装使用独立 BuildKit 缓存，缓存不写入最终镜像；浏览器安装完成后会复制到镜像内的 `/opt/playwright`，容器运行时无需临时安装浏览器。pip 仍校验锁文件中的所有哈希。更新软件源会使部分构建层重新执行，基础镜像及未受影响的前端层可复用；旧版本尚未完成的 pip 步骤使用了 `--no-cache-dir`，其下载不能承诺保留。新版本后续失败重试可复用已成功缓存的下载。不要用 `--no-cache` 或清理构建缓存来处理网络慢的问题。

日志分成基础镜像、应用构建、启动检查三个阶段，构建使用完整文本日志。npm 锁文件完整性、Python 锁文件哈希及 TLS 校验仍然保留；脚本不修改 Docker 全局配置或重启 Docker。

技能安装、MCP 连接与资料空间已接入网页版。具体入口、目录、认证方式及回收站行为见[技能与 MCP 及资料空间](技能与MCP及资料空间.md)。备份时请同时保留数据卷与工作卷，资料索引和回收站位于数据卷中。

### 排查远程访问的来源校验失败

出现“请求来源不匹配，请从部署地址重新打开页面”时，网关会在容器日志输出
`origin_rejected` 警告。这不改变认证策略，也不需要开启调试模式或修改密码。

在包含此改动的源码目录重新构建并启动容器（会短暂重启服务，沿用原有 `.env`、密码和数据挂载）：

```sh
docker compose up -d --build knowe
docker compose logs --since=5m -f knowe
```

从原来失败的 App 页面重试一次登录，查看 `origin_rejected` 那一行：

- `origin`：请求实际携带的来源，包含规范化的 `scheme`、`host`、`port`。
- `server`：网关自身看到的协议、主机和端口，不信任任意转发头。
- `configured`：是否配置了 `KNOWE_WEB_ORIGIN`。
- `expected`：当前校验所期望的来源。
- `state` 区分 `missing`（无 Origin）、`null`、`empty`、`invalid` 与 `valid`。

日志只保留通过校验的来源组成部分，省略路径、查询、片段；含用户凭证、控制字符或
异常格式的值仅记录 `invalid`，不打印原文。不记录密码、Cookie、Authorization 或请求正文。
日志中的主机名/IP 仍是部署信息，分享时仅提供相关一行并按需打码。
日志的规范化仅用于诊断，实际来源比较规则不变；不要仅凭中转服务域名修改允许来源，
也不要把 `null`、空来源或整个共享域名通配放行。成功登录不输出此警告。

### 极空间 App 本地代理兼容（默认关闭）

如果已确认极空间远程应用使用隔离的浏览器存储和可信本地代理，且失败日志显示
`origin` 为 `http://127.0.0.1:端口`、`server` 为 NAS 内网地址，可在原部署目录
`.env` 中新增或修改以下一项：

```dotenv
KNOWE_WEB_ZSPACE_COMPAT=1
```

更新到包含此功能的源码后，运行 `docker compose up -d --build knowe`，等健康检查通过，
重新打开 App 页面并登录。配置只需开启一次，不必随代理端口变化反复修改。
无需把 `KNOWE_WEB_ORIGIN` 改为 localhost 或极空间中转域名；原内网来源判定保留。
默认 HTTP 内网部署仍保持原有 Cookie 设置，不要仅为此模式开启 Secure Cookie。
如原部署使用 HTTPS/Secure Cookie，应单独验证 HTTP App 入口是否保存会话，不要贸然降低原 HTTPS 配置。

兼容范围严格限于 `http://127.0.0.1:1` 至 `http://127.0.0.1:65535` 的显式端口形式，
拒绝省略端口、前导零、路径、查询、用户名密码、其他 IP、localhost 域名、HTTPS、空来源和 `null`。
原密码、会话、写请求及 WebSocket 检查仍生效；兼容来源不是免登录。
这只是来源检查的显式例外，不能证明请求来自极空间，不能防御恶意同源应用或泄漏的会话。
仅在信任终端、代理与应用存储隔离的前提下开启；极空间账号登录不能替代 Knowe 认证。
将此项改为 `0` 并运行 `docker compose up -d knowe` 可恢复默认严格来源策略。

更新会重启服务，请先等活动任务结束。验收时分别检查内网和 App 登录、上传、聊天连接、刷新、注销；
若仍失败，查看 `docker compose logs --since=5m -f knowe` 中的错误，勿分享密码或 Cookie。
